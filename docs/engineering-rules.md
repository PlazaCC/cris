# Engineering Rules

## Purpose

This document defines the technical baseline for:

- Clean Architecture with dependencies pointing inward
- Separation of concerns between UI, domain, and data layers
- Best practices for typing, validation, and security
- Adherence to official documentation for the stack versions in use

## Clean Architecture Baseline

### Web Structure

Layers and responsibilities:

- `pages/` and route components: presentation and composition only.
- `components/`: visual components and reusable blocks without business logic.
- `features/<x>/`: use cases grouped by functional context — `api.ts` (server functions), `schemas.ts` (Zod input schemas), `hooks/` (TanStack Query).
- `server/`: server-only code (database, auth, mailer, sanitizer, crypto). Imported only by `features/*/api.ts`, server routes and `scripts/`.
- `lib/adapters/`: database row → domain type mappers. `lib/`: other technical utilities.
- `interfaces.ts`: domain types, the contract between data and UI.

Rules:

1. UI never touches data directly: components use hooks from `features/*/hooks`, hooks call server functions from `features/*/api.ts`.
2. Database rows never leak into components without mapping to domain types.
3. Validate input and output at boundaries with Zod.
4. Data hooks using TanStack Query live in `features/*/hooks` not inside generic UI components.

### Routing and SSR (TanStack Start)

The web client is rendered on the server with TanStack Start.

- Routes are file-based in `src/routes/` (`routeTree.gen.ts` is generated by the Vite plugin — never edit it by hand, commit it).
- `src/router.tsx` exports `getRouter()`, which creates one `QueryClient` per request and wires `setupRouterSsrQueryIntegration`.
- Route files only wire things together (loader, `head`, `component`). Page components live in `pages/`.
- Each hook in `features/*/hooks` also exports its `xxxQueryOptions()`. Route loaders prefetch with `context.queryClient.prefetchQuery(xxxQueryOptions())` — never `ensureQueryData`, so a data failure renders the section's `ErrorState` instead of breaking the whole route.
- Page metadata (title, description, favicon) is set via the route `head()`, never by mutating `document`.
- When a loader needs the data itself (redirect, `notFound`, `head`), it prefetches and then reads it with `getQueryData`. A `null` result means "does not exist" (`notFound()`); a query error stays in the cache so the page renders its `ErrorState`.
- Projects live at `/work/$slug`; `/work` redirects to the first project in home order, and "Next Project" follows that order, wrapping from the last to the first.

### Responsive layout

The Figma file has a Mobile page (360–400px frames) for every screen; desktop is the 1440px frame.

- Write classes mobile-first: the base classes follow the Figma Mobile frame and the breakpoint classes restore the desktop frame.
- `md` (768px) switches navigation (the compact mobile menu ↔ the desktop pill) and the home project cards; `lg` (1024px) switches two-column layouts and desktop type sizes (About hero, project header, content blocks). Below `lg` everything stacks.
- Mobile side gutter is 20px (`px-5`); desktop keeps the Figma paddings (`px-10`, `px-[155px]`).
- Text sized to fill the width (e.g. the footer brand) scales with the viewport and is capped at the Figma size, so it never overflows narrow phones.
- Data is read through server functions (`createServerFn`) in `features/<x>/api.ts`. Hooks call them from `queryFn`; components never import `server/` or `api.ts` directly.
- Code that touches `window`, `document` or `localStorage` must run only on the client (effects, event handlers, or behind `typeof window` checks). `locomotive-scroll` is initialized in `lib/smooth-scroll.ts` and accessed via `getSmoothScroll()`.

### Data Layer (Drizzle + Neon)

Content lives in Postgres (Neon) and is read directly by the web server through server functions. It is edited in the app's own panel (`/admin`, below); there is no separate CMS service.

- `src/server/db/schema.ts` — Drizzle tables. Single types (`site_global`, `about`, `footer`) have exactly one row (`id = 1`, enforced by a check constraint).
- Nested content (`ProjectBlock[]`, `ResponsiveImage`, lists) is stored as `jsonb` in the same shape as the domain types in `interfaces.ts`.
- `src/server/db/json-types.ts` — Zod schemas for every `jsonb` field. Adapters must parse `jsonb` with them: the database is a boundary too.
- `lib/adapters/*-adapter.ts` map **database row → domain type**. A missing single-type row maps to defaults instead of an error state.
- Server-only env vars (`DATABASE_URL`, `BLOB_READ_WRITE_TOKEN`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`) are read from `process.env` and must never use the `VITE_` prefix.
- Schema changes: edit `schema.ts` → `yarn workspace client-web db:generate` → commit the SQL in `drizzle/` → `db:migrate`. Never edit applied migrations.
- Seed: `yarn workspace client-web db:seed` (idempotent; uploads `seed/uploads` to Vercel Blob and upserts `seed/data.json`).
- Writes are `createServerFn({ method: 'POST' })` in the same `features/<x>/api.ts`, always with `.middleware([authMiddleware])` (`server/auth-middleware.ts`: no session → 401) and `.validator()` using the input schema from `features/<x>/schemas.ts`. The admin form uses the same schema with `zodResolver`, so client and server validate the same shape.
- Mutation hooks live next to the query hooks (`features/<x>/hooks/use-update-x.ts`, `use-x-mutations.ts`) and update or invalidate the affected query keys on success.
- neon-http has no interactive transactions: multi-statement writes use `db.batch([...])`, which runs as one transaction.
- HTML that the public site renders with `dangerouslySetInnerHTML` (scope and paragraph blocks) is sanitized on write with `server/sanitize.ts`. Never render admin-provided HTML that skipped it.
- CommonJS-only packages whose default export breaks in SSR are re-exported once with an interop guard (see `components/ui/marquee.ts`).

### Deploy (GitHub Actions → Vercel)

- Only `.github/workflows/deploy.yml` deploys; Vercel git deploys are disabled in `clients/web/vercel.json`.
- On `main`: build first, then migrations (`DATABASE_URL_UNPOOLED`, direct connection), then `vercel deploy --prebuilt --prod`. A failed build never touches the database.
- Migrations run before the new code is live, so they must be backward compatible with the deployed version (add columns/tables first; drop or rename in a later deploy).
- App env vars live only in the Vercel project (Production) and reach CI through `vercel pull`; GitHub only holds the Vercel token and IDs.
- `vite dev` does not bundle dependencies, so it hides bundling bugs. CI runs `clients/web/scripts/smoke.sh` (boots `.output` with a fake database and checks a few routes) before anything touches production. Run it locally after dependency changes: `yarn workspace client-web build && bash clients/web/scripts/smoke.sh`.
- Keep a single major version of shared runtime deps (e.g. `zod` 4, which Better Auth requires). Nitro rebundles the SSR output from the project root, so a dependency's nested copy is not used in production.

### Admin panel (`/admin`)

- Auth: Better Auth (`server/auth.ts`), email + password only, public sign-up disabled. Accounts are created with `yarn workspace client-web auth:create-admin <email> <password> [name]` (also resets the password of an existing account). The HTTP handler is `routes/api/auth/$.ts`; the browser client is `lib/auth-client.ts`, used only through `features/auth/hooks`.
- Routes: `routes/admin/login.tsx` and the pathless layout `routes/admin/_panel.tsx`, whose `beforeLoad` calls `getAdminUser()` and redirects to `/admin/login` without a session. Every page under `_panel/` inherits the guard; the guard is UX only — the real protection is `authMiddleware` on every write.
- The panel does not use `AppLayout`: Menu, Footer, page transitions and smooth scroll belong to the public site (`pages/_layout.tsx`), not to `__root.tsx`.
- Media: the browser uploads straight to Vercel Blob (`upload()` + token from `routes/api/upload.ts`, which checks the session, accepts `image/*` up to 20 MB) to avoid the 4.5 MB function body limit, then calls `registerMedia`, which confirms the file with `head()` and saves it in `media`. No `onUploadCompleted` webhook, so it also works on localhost. Deleting a media item is refused while its URL is still used by any project, About or Global.
- The block editor mirrors `ProjectBlock`: one editor per block type in `pages/admin/components/block-editor.tsx`. Adding a block type means updating `interfaces.ts`, `json-types.ts`, the public block component and this editor together.

### Contact form and e-mail

- The "get in touch" button (`components/menu.tsx`) opens `components/contact-dialog.tsx`, which calls the public `submitContactMessage` (`features/contact/api.ts`).
- **Save first, e-mail second.** The message is inserted in `contact_messages` before any SMTP call, so it is never lost; the visitor gets success either way. `server/mailer.ts` (`notifyContactMessage`) then records the result in `email_status`: `sent`, `failed` (with `email_error`), `disabled` (sending off in the panel) or `pending` (the request died mid-send). `/admin/messages` flags `failed`/`pending`, shows the error and can resend; the sidebar badge turns red while any message is unflagged.
- SMTP is configured in `/admin/email` (`mail_settings`, single row), not in env vars. The password is encrypted with AES-256-GCM (`server/secret-box.ts`, key derived from `BETTER_AUTH_SECRET`) and never returned to the browser (`MailSettings.hasPassword` only). Rotating `BETTER_AUTH_SECRET` means re-entering the SMTP password. "Enviar teste" uses the saved settings, even with sending off.
- Sending happens inside the form request with short nodemailer timeouts (10–15 s). Vercel blocks outbound port 25; use 465 (SSL) or 587 (STARTTLS).
- Abuse: hidden honeypot field `website` (filled ⇒ fake success, nothing saved) and a rate limit of 5 messages per IP per 10 minutes, keyed on a salted hash of the IP (`ip_hash`), never the raw IP. Messages are plain text: rendered as text in the panel and sent as `text/plain`.

### Page transitions (shared cover)

- `AppLayout` (`pages/_layout.tsx`) animates every page change with `AnimatePresence mode="wait"`. By default (menu, Back, Next Project) the old page slides sideways and fades out, with no scale. The direction follows the menu order (`lib/menu-items.ts`): moving forward (intro → about → work) the old page leaves to the left and the new content enters from the right; moving back, the reverse. `AppLayout` computes it in the router's `onBeforeNavigate`, which also covers the browser's Back, and stores it in `page-transition-store`. The exit reads it through the `AnimatePresence` `custom`, and `revealItem` reads it from the store, since inherited variants don't receive the parent's `custom`. The new page's above-the-fold content then enters in order: each page marks those blocks with `variants={revealItem}` (`components/page-transition/reveal.ts`), which inherit the wrapper's `initial` → `enter` states and are staggered by it (`staggerChildren`). Reveal items have no `initial`/`animate` of their own, or they stop inheriting.
- Pages stay mounted during their exit, after their route is no longer active. Page components must not use hooks that throw without an active match (`getRouteApi(...).useParams()`). Read params with `useParams({ from, shouldThrow: false })` and keep the value from mount, as `pages/work/index.tsx` does.
- Scroll between pages belongs to `AnimatedOutlet`, which scrolls to the top when the next page mounts. Browser scroll restoration is set to `manual`, and links use `resetScroll={false}`.
- Clicking a home project card starts a **shared cover** transition: `beginCoverTransition` (`components/page-transition/shared-cover-target.ts`) saves the card's position and image in `stores/page-transition-store.ts`, and `SharedCoverOverlay`, which sits outside the `AnimatePresence`, flies that image to where the project cover will be.
- A page transition is choreographed as a whole, never just the focal animation. It runs in three beats (`COVER_TIMING` in `shared-cover-target.ts`):
  1. **Out**: the current page animates its own content out with `coverContentOut`. On the home: the hero, the other cards, the pagination, and the clicked card's info panel. The clicked image stays still. When the out ends, the overlay (already decoded) takes the card's place and the source card turns `invisible` in the same frame (`launched` in the store), so the image is never on screen twice. A clicked card that is mid-stack (blurred and scaled by the scroll effect, partly covered by the next card) first comes forward: its `release` motion value undoes the blur and scale while the covering card fades, and the flight starts from the card position measured at launch, not at click.
  2. **Flight**: only the cover moves. `AppLayout` keeps the old page mounted and still until the cover lands (counted from the click), so mounting the next page never competes with the flight for frames.
  3. **In**: the new page mounts with the cover already in place. Its content enters with `coverContentIn`, gated by `useCoverEntering(slug)`, which is read once on mount, so SSR and direct visits render without animation.
- The landing spot is predicted before the project page exists: the overlay measures an invisible copy of the header built from the same `ProjectCoverFrame` + `projectHeaderClassName` (`components/page-transition/project-cover-frame.tsx`). Changing the project header's cover layout means changing that shared frame, never a copy of it.
- `ProjectHeader` uses `useSharedCoverTarget(slug)`: it hides its cover while the overlay is flying, then reports the real position after the image decodes. The overlay corrects to that position and fades out over the real cover. If no page takes over (error, 404), the overlay leaves on its own after a timeout.
- Links that trigger an animated page change use `resetScroll={false}`: `AnimatedOutlet` scrolls to the top when the next page mounts, and the router's reset would jump the old page while it is still on screen. The exiting page uses `overflow-clip`, never `overflow-hidden`, which would create a scroll container and break the cards' `position: sticky` mid-exit.
- New cover handoffs (e.g. Next Project with an image) reuse the same store and hooks. The transition is skipped with `prefers-reduced-motion` and for clicks that open a new tab.

### Home Hero (static, animated)

The home hero is **designed content, not CMS content**: it lives in code (`pages/home/components/hero/`) and is the one exception to "no hardcoded content". Its copy and illustrations come from the Figma file (Desktop and Mobile pages), and changing it is a design + code change.

- `art.tsx` — one illustration per discipline (Type, 3D, Motion, Visual, Experience), desktop and mobile, placed with Figma coordinates via `stage.ts`.
- `stage.ts` — `place(x, y, w, h)` positions an element in Figma px of a fixed frame (desktop 1360×830, mobile 360×690); `stageVars()` scales the frame to the card with container query units (`--u`). Needs an ancestor with `container-type: size`.
- `animations.ts` — per-slide GSAP enter + idle + exit timelines (each exit sets up the next enter; `handoff` is how much of the end of an exit runs together with the next enter, as in the Motion → Visual camera move), targeting `data-*` hooks (`data-draw`, `data-piece`, `data-float`, `data-spin`) and Figma layer names (`data-name`).
- `index.tsx` — a single looping master timeline (word swap, art, progress bar) inside `useGSAP` + `gsap.matchMedia()`; it pauses offscreen and does not run with `prefers-reduced-motion` (static Polymath state, which is also the SSR output).

Rules:

1. Inline Figma SVGs with `components/ui/inline-svg.tsx` (`?raw` import + unique `scope`). It prefixes ids deterministically (`lib/svg.ts`) so gradients/masks don't collide and SSR matches hydration.
2. Everything except the initial state starts hidden via CSS (`invisible` / `hidden`) and is revealed by GSAP, so there is no flash before hydration.
3. Don't use Tailwind `scale-*`/`rotate-*`/`translate-*` on elements GSAP transforms: Tailwind 4 sets the individual `scale`/`rotate`/`translate` properties, which compound with GSAP's `transform`.
4. Measure text at animation time, not on mount — web fonts may load after hydration.
5. Pieces that start later in a stagger get their from-state with `set` at time 0 (then `to`), otherwise they show their final state until their turn.
6. In dev the master timeline is exposed as `window.__heroTimeline` for pausing/seeking while reviewing the choreography.

## Content Rules

### Modular Single Types

Single types are split by responsibility, one table each:

- `site_global`: site name, description, favicon, default SEO.
- `about`: About page.
- `footer`: footer content.

Rules:

1. UI never contains mocked data as visual fallback. Initial content lives only in the seed (`clients/web/seed/data.json`).
2. Components consume data via hooks and adapters.
3. Error and loading states preserve the section layout.
4. A single type that was never saved has no row: the adapter maps that to defaults, never to an error state.

### Schema Changes Require End-to-End Updates

Adding or changing a content field means updating, together:

- `server/db/schema.ts` (+ a generated migration) and, for `jsonb`, `server/db/json-types.ts`.
- The domain type in `interfaces.ts` and the adapter in `lib/adapters/*`.
- The input schema in `features/<x>/schemas.ts` and the server functions in `features/<x>/api.ts`.
- The admin form in `pages/admin/*` and the consuming public components.

## Conventions and Quality

- TypeScript strict mode must stay enabled in the web client.
- Avoid `any`. When unavoidable encapsulate and document the reason.
- React components use `PascalCase`. Utility files use `kebab-case`.
- Do not mix styling, domain state, and I/O responsibilities in the same module.
- Justify all new dependencies and add them to the stack section of this document.

### TanStack Query Requirements

All `useQuery` and `useMutation` hooks must include `refetchOnWindowFocus: false` to prevent unnecessary network churn:

```typescript
useQuery({
  queryKey: ['resource'],
  queryFn: async () => {
    /* ... */
  },
  staleTime: 1000 * 60 * 10,
  gcTime: 1000 * 60 * 30,
  refetchOnWindowFocus: false,
})
```

### Adapter Pattern

Adapters (`lib/adapters/*-adapter.ts`) map database rows to domain types. Always:

1. Type the input as the Drizzle row (`typeof table.$inferSelect`)
2. Parse `jsonb` fields with the schemas from `server/db/json-types.ts`
3. Return the domain type from `interfaces.ts` — never the raw row (dates become ISO strings, secrets never leave the server)

### Zustand State Usage

`stores/` is reserved for **cross-cutting UI state** with no natural feature owner:

- Navigation lock (`navigation-store.ts`) ✓
- Page transition handoff (`page-transition-store.ts`) ✓
- Feature-specific state (filters, highlights) → Use feature hooks instead ✗

### Domain Type Contracts

Domain types live in `src/interfaces.ts`. Database rows are typed from `server/db/schema.ts`. Adapters bridge the two, ensuring components only see domain types.

## Definition of Done

A task is complete when:

1. It respects layers with no dependency violations.
2. It has consistent typing end to end.
3. It does not keep mocks inside final components.
4. It passes lint and build for the changed package.
5. It updates docs when introducing new architectural decisions.
